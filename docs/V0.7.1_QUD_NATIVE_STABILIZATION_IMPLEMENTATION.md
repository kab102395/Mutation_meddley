# Mutation Meddley v0.7.1 — Qud-Native Stabilization Implementation Audit

This document records what was actually changed during the Qud-native stabilization sweep and completion sweep, and what still requires the authoritative Caves of Qud compiler/runtime.

The governing plan is `docs/V0.7.1_QUD_NATIVE_STABILIZATION_SWEEP.md`.

The engineering rule for this patch is:

> Mutation-owned behavior is owned by the mutation. Shared services coordinate reusable transactions. Biology is an aggregate player inspector, not a second mutation engine.

## 1. Qud-native structure retained

The implementation continues to use the ordinary Qud scripting-mod surfaces already used successfully by the project:

- mutation parts
- registered command events
- activated abilities
- `PlayerMutator` for new-game initialization
- `CallAfterGameLoaded` for loaded-save repair
- `RequirePart` for player support composition
- 1000 energy for a normal deliberate mutation action
- zero-energy inspection
- the existing serialized mutation-state envelope

No Harmony patch was introduced.

No unseeded `System.Random` path was introduced.

No speculative HUD, attack-type, body-plan, gas, liquid, or minimal-event API was added.

## 2. Player-global Biology bootstrap

The first `0.7.1` build relied too heavily on one support-part installation moment. Hands-on testing showed that the build could compile while `Mutation Meddley Biology` and the new deliberate action abilities were missing from a new character.

The stabilized bootstrap now has independent repair paths:

1. `PlayerMutator` installs the support on a new player.
2. `CallAfterGameLoaded` installs/refreshes it on loaded saves.
3. every adaptive Mutation Meddley mutation defensively ensures the support when registered/gained
4. every adaptive mutation checks again during normal EndTurn lifecycle
5. `MutationMeddley_EnsureInstalled` immediately restores the Biology inspector if the support part already exists but the inspector GUID/button was pruned

The global hooks use their supplied object as the player by contract instead of requiring early `IsPlayer()` visibility during character construction.

Mutation-side repair remains player-guarded so NPC mutations do not acquire player UI.

## 3. No-MM and former-player behavior

Because the new-game hook runs for every player, Biology can be created before the final mutation list is known.

The stabilized behavior is:

- early character construction may temporarily create Biology
- after gameplay starts, a body with no MM mutation prunes the inspector
- the part does not enter a create/remove loop every turn
- gaining an MM mutation later restores Biology through the mutation-side ensure path
- if a body stops being the player, Biology becomes inert and its player UI is removed

This keeps one compatibility-safe support part without treating the inspector as NPC biology.

## 4. Mutation-owned primary activated abilities

The first player-agency implementation made `MutationMeddley_BiologySupport` own all five primary action buttons.

That was structurally wrong and has been replaced.

Each `MutationMeddley_AdaptiveMutationBase` now:

- registers its own primary action command
- owns its primary activated ability lifecycle
- recreates a missing/stale primary ability GUID
- stores action GUID/signature metadata in its own existing evolution-state envelope
- replaces the button exactly when the rank-3 identity changes
- updates the description without recreating the button when only meter state changes
- removes the action on mutation removal
- removes the action while Carapace Evolution is functionally dormant

The action metadata keys are:

- `primary_action_guid`
- `primary_action_signature`

No new public mutation fields were added.

## 5. Primary action transaction logic extracted from Biology UI

The first `0.7.1` action implementation also put the actual resource-spend/conversion/healing/energy transaction inside the Biology partial class.

That has now been removed.

`Code/MutationMeddley_PrimaryActionService.cs` owns the reusable deliberate-action transaction implementation.

Biology's `ActionsA` file is now only a thin routing bridge that supplies:

- mutation
- owner
- action signature
- action name
- action description

The service then performs the one authoritative transaction.

This means the bottom-bar mutation command and the Biology menu route to the same action implementation rather than maintaining two copies.

## 6. Deliberate action transaction contract

The action service follows one transaction order:

1. require a live player owner and mutation
2. require functionally active mutation biology
3. validate resource/state requirements
4. if invalid, fail without resource spend or energy spend
5. perform the resource spend/conversion
6. perform the effect
7. refresh the mutation's passive/action surface
8. refresh Biology telemetry
9. spend exactly 1000 energy
10. emit one meaningful player message

Current branch-aware primary actions remain:

- Carapace Evolution — Brace Shell / Fortify Shell / Drive Shell / Discharge Attunement
- Living Crystal — Resolve Crystal Stress / Refract Lattice / Resonant Release
- Brineborn — Draw Brine / Raise Saltglass / Release Wake
- Ash Metabolism — Cauterize / Bank Kiln / Stoke Rush / Gather Haze
- Walking Colony — Redistribute Pressure / Knit Flesh / Map Pursuit / Delegate Load

## 7. Retune lifecycle correction

`Retune ...` is no longer present before there is an actual stance to select.

Current contract:

- rank 1/2 -> no Retune button
- rank-3 identity selected -> Retune appears
- Carapace Evolution dormant -> Retune disappears
- reselect current stance -> no energy spent
- select a different stance -> 1000 energy

The mutation description also no longer tells a pre-rank-3 player to use an ability that does not exist; it reports that stance controls unlock with the identity.

## 8. Stale Evolve ability repair

The original Evolve ability lifecycle used a public GUID field. An old save can theoretically preserve a non-empty GUID while the corresponding `ActivatedAbilities` entry is absent.

`Code/MutationMeddley_AbilityRepair.cs` now provides an explicit migration repair for the five adaptive gameplay mutations.

During Biology maintenance it:

- verifies the saved Evolve GUID is still present
- clears a stale GUID
- recreates the standard Evolve activated ability if necessary
- restores the standard description

The actual Evolve command event and evolution choice mechanics remain mutation-owned.

`Evolution Seed [DEV]` is not included in this player-facing adaptive repair loop; it is a development mutation rather than one of the five shipped gameplay mutation families.

## 9. First-0.7.1 action migration

The initial `0.7.1` support part introduced public GUID/signature fields for support-owned action buttons.

Those fields are deliberately retained so the serialized class layout is not changed mid-test-release.

They are now migration-only.

Biology removes any legacy support-owned action entries and clears their legacy signatures while the current mutation-owned buttons repair themselves from each mutation's state envelope.

## 10. Biology is aggregate UI, not gameplay owner

`Mutation Meddley Biology` remains one player-global activated ability.

It owns aggregate inspection only:

- owned MM mutations
- ranks/paths/stances
- current/max resources
- resource flow descriptions
- deliberate-action descriptions
- automatic reaction telemetry
- Mutation Meddley stat contribution summaries
- active synergies/ecology

It does not register the five mutation-specific action command events.

It does not directly spend action energy.

Its `ActionsA` bridge no longer contains the concrete resource transaction keys.

## 11. State-envelope parsing extracted from Biology

Biology originally reimplemented the serialized `MutationMeddley_EvolutionState` parser/writer.

That created a second implementation of the state contract.

The generic parser/writer now lives in:

`Code/MutationMeddley_StateEnvelopeAccess.cs`

It provides:

- `HasAnyEvolution`
- `HasEvolution`
- integer metadata read
- integer metadata write
- preservation of selected evolution IDs
- preservation of unknown metadata keys
- deterministic metadata-key ordering
- `statev=1` maintenance

`MutationMeddley_BiologySupport.StateA.cs` is now only a thin bridge to this shared framework service.

This does not yet eliminate every UI-side resource-cap formula, but it removes direct serialized-envelope parsing from the UI layer.

## 12. Resource telemetry cap corrections

Static comparison between the concrete mutations and Biology found real display drift.

### Ash Metabolism

The first Biology implementation omitted the lit Photosynthetic Skin cap contribution.

Current displayed Ember cap now matches the concrete rule:

- base 6
- +1 Flaming Ray
- +1 Photosynthetic Skin while lit

### Brineborn

Displayed Reserve cap mirrors:

- base 6
- +1 Amphibious
- +1 Photosynthetic Skin while lit

### Walking Colony

Displayed Pressure cap now mirrors the known current `BODY_PART_INTERACTION` registry used by the concrete mutation:

- base 6
- +1 Multiple Legs
- +1 if another compatible body interaction exists among Carapace, Quills, or Burrowing Claws

The long-term architecture should still replace these copied formulas with concrete read-only telemetry providers. For this recovery release, the copies were audited against the current concrete code rather than left knowingly divergent.

## 13. Reaction telemetry corrected against actual spend paths

The completion sweep re-read the concrete reaction handlers and corrected several Biology statements that were too loose.

### Brineborn

- Wellspring incoming recovery now reports **1 Mend** as the reaction resource; Reserve can generate Mend but is not the direct incoming reaction spend.
- Saltglass reports **1 Bastion** as the pressure/contact spend.
- Scouring reports **1 Wake** on qualifying adjacent engaged melee contact; movement/tide posture generates Wake but is not an additional spend condition once Wake is stored.

### Ash Metabolism

- Furnace incoming response now reports **1 Kiln**, not `Kiln or Embers`.
- Cinder contact now reports **1 Rush`; movement/heat feeds Rush, but stored Rush can survive until a qualifying contact.
- Smoke response now reports **1 Haze**, not `Haze or Embers`.

### Walking Colony

- Surveyor reaction explicitly distinguishes Scout availability from the movement/contact trigger.

The patch still does not invent random percentages. Existing deterministic reactions remain deterministic and expose `0%`, `100%`, or `100% when the documented trigger qualifies` according to currently knowable state.

## 14. Shared healing path completed

The continuous-rank contract says rank-4/7/10 verb growth strengthens existing mutation verbs.

Three historical concrete paths still used direct `ParentObject.Heal(...)`, bypassing that shared scaling:

- Carapace + Regeneration stationary recovery
- Brineborn Draw Brine automatic recovery
- Walking Colony Knit Flesh automatic recovery

All three now route through the adaptive `MutationMeddley_TryHeal(...)` helper.

The only direct `ParentObject.Heal(...)` call allowed by the repository is now the base implementation inside `MutationMeddley_EvolvingMutationBase.MutationMeddley_TryHeal` itself.

The preflight enforces that invariant.

## 15. Passive-stat/max-HP repair retained

The earlier `0.7.1` health repair remains intact:

- fast-changing Brace no longer modifies Toughness/max HP
- unevolved active Brace reinforces shell defense instead
- passive stats are accumulated into a desired snapshot
- Qud stat shifts are committed only when the final value changes
- unchanged Toughness is not deliberately zeroed/re-added on routine movement/damage refreshes

This is specifically intended to prevent Mutation Meddley from causing max-HP oscillation around vanilla `Tighten Carapace` and vanilla low-health warning thresholds.

## 16. Spiteful Wall internal churn removed

The earlier static audit found a contradictory pair:

- concrete Carapace turn logic decremented Brace while engaged
- shared stabilization code restored a Brace point while stationary in Spiteful Wall

The intended net behavior was that stationary Spiteful Wall should preserve its stored Brace for actual incoming pressure.

The completion sweep removed the canceling architecture:

- the concrete engaged decrement is now limited to engaged **non-stationary** Spiteful behavior
- the shared stationary compensation block was removed
- the mechanic note now describes the actual preserved-Brace behavior

This eliminates hidden decrement/re-add churn without changing the intended player-facing stationary result.

## 17. Damage/contact resource safety retained

The existing generic stored-state consume gate remains important.

For outgoing `AttackerDealtDamage` context, the shared resource consumer refuses the spend unless the current context qualifies as the mod's conservative melee-contact context.

Concrete strike handlers resolve the target/context before consuming their stored state.

That means a stored Wake/Rush/Impact/Scout-style meter is not supposed to be spent merely because `AttackerDealtDamage` fired from a non-contact ranged attack.

The known adjacent-ranged-while-engaged edge case still requires runtime tracing; no guessed attack-type API was introduced.

## 18. Bonus-damage result semantics remain explicit

The shared damage result distinguishes:

- `DamageDispatched`
- event continuation
- observed HP loss

The completion sweep did not globally replace one concept with another.

The enhanced preflight now lists every `.DamageDispatched` consumer as a warning so those branches remain visible for supported-build runtime review.

This is intentionally a runtime semantic gate rather than a speculative static rewrite.

## 19. Environmental damage double-event gate remains runtime-only

Several mutation families register both:

- `TookDamage`
- `TookEnvironmentalDamage`

Static source inspection cannot establish whether one environmental incident in the supported build enters both event routes.

No guessed dedupe token was introduced.

Runtime acceptance must use DEV trace and one controlled environmental incident to determine whether one underlying event is being processed twice.

## 20. Environment predicates remain a known heuristic layer

Wet/saline/hot/smoky predicates still contain heuristics already used by the mod.

The completion sweep deliberately did not replace working behavior with unverified Qud APIs.

Formal predicate consolidation remains part of the later environment/ecology architecture work.

## 21. Serialization policy

The current support and mutation classes already exist in test saves.

`0.7.1` therefore does not attempt a mid-release conversion of established classes to another serialization model.

The patch preserves:

- existing public fields
- existing `MutationMeddley_EvolutionState`
- evolution IDs
- stance metadata
- resource metadata
- hidden progress keys
- unknown metadata keys

Migration-oriented serialization modernization belongs in a dedicated later compatibility pass with old-save fixtures.

## 22. Preflight substantially expanded

`tools/check.sh` now catches or surfaces the main structural regressions discovered during the `0.7.1` development cycle.

Hard failures include:

- missing manifest values or wrong mod ID
- malformed `Mutations.xml`
- duplicate mutation names/classes in XML
- registered mutation class missing from source
- unprefixed registered mutation class
- checked-in DLLs
- duplicate Biology `[Serializable]` partial declarations
- `MutationMledley_` typo
- missing/duplicated new-game/load lifecycle hooks
- mutation action commands accidentally registered back on Biology
- missing primary-action service or transaction markers
- Biology ActionsA directly spending energy/resource state again
- missing centralized state-envelope service
- Biology StateA regaining direct parser implementation
- missing stale-Evolve repair service/maintenance hook
- missing mutation-owned primary action lifecycle markers
- unseeded `new Random()`
- Harmony use in the `0.7.1` stabilization release
- any direct `ParentObject.Heal(...)` outside the single shared base helper

Warnings keep visible:

- obsolete `Register(GameObject)` overrides
- obsolete `Popup.ShowOptionList` calls
- every `.DamageDispatched` consumer requiring runtime semantic review

The preflight is still a static repository gate. Qud remains the authoritative C# compiler/runtime.

## 23. What the static completion sweep now considers closed

The following previously open code-level items are now closed in source:

1. Biology bootstrap has multiple defensive installation/repair paths.
2. Biology-reinstall-after-prune hole is fixed.
3. mutation-specific buttons are mutation-owned.
4. mutation-specific action command events are mutation-owned.
5. primary action gameplay transactions no longer live in Biology UI.
6. Biology and bottom-bar actions share one transaction implementation.
7. dead rank-1/2 Retune buttons are removed.
8. same-stance selection does not spend energy.
9. first-0.7.1 legacy action buttons are migration-cleaned.
10. stale primary-action GUIDs repair.
11. stale adaptive Evolve GUIDs repair.
12. Biology no longer directly parses/writes the serialized envelope.
13. known Ash/Brine/Walking resource-cap display drift is corrected.
14. several misleading reaction-resource descriptions are corrected against concrete handlers.
15. all concrete direct-heal bypasses are removed.
16. stationary Spiteful Wall no longer relies on decrement/restore compensation.
17. duplicate Biology serialization is guarded against.
18. no Harmony/unseeded-RNG regression is allowed by preflight.

## 24. What still requires the installed Qud build

The following cannot be truthfully closed through GitHub/static inspection alone:

1. exact branch compiles against Caves of Qud `BUILD_2_0_211`
2. `PlayerMutator`/mutation construction timing produces Biology + primary buttons immediately on an actual new game
3. old-save load reconstructs the exact ability set without duplicates
4. ability descriptions render acceptably in the current UI
5. all nested Biology option lists behave correctly with controller
6. primary action invocation from Biology and bottom bar produces identical energy/resource results
7. Tighten/untighten no longer experiences MM-driven Toughness/max-HP churn
8. environmental damage does or does not enter both registered damage events
9. adjacent ranged attacks while already engaged do or do not satisfy the conservative contact gate
10. `.DamageDispatched` is the correct branch decision in every listed consumer on the supported build
11. the nonserialized applied-stat cache reconstructs correctly over a real save/reload
12. no runtime exceptions or message/proc cascades occur under stacked-mutation play

These are mandatory runtime gates, not optional polish.

## 26. New-game acceptance matrix

Create a new character with vanilla Carapace + Carapace Evolution + Walking Colony.

Before intentionally spending a turn, inspect abilities.

Expected rank-1 player-facing set includes:

- `Mutation Meddley Biology`
- `Brace Shell`
- `Redistribute Pressure`
- `Evolve Carapace Evolution`
- `Evolve Walking Colony`

Expected absent at rank 1:

- `Retune Carapace Evolution`
- `Retune Walking Colony`

After one normal turn the ability set must remain stable and nonduplicated.

## 27. Evolution/action lifecycle matrix

For each of the five gameplay mutation families:

- rank 1 -> baseline primary action exists
- rank 2 -> same action, updated scaling/cap where appropriate
- rank 3 identity -> baseline action is replaced by exactly one branch action
- rank 3 identity -> exactly one Retune appears
- select current stance -> no energy
- change stance -> 1000 energy
- rank 6 -> action remains coherent with specialization
- rank 9 -> action remains coherent with capstone/unusual endpoint
- mutation removal -> mutation-owned action/Retune/Evolve removed by normal lifecycle
- save/reload -> exact action set reconstructs once

For Carapace Evolution additionally:

- remove vanilla Carapace -> MM shell action/Retune disappear while evolution state remains
- regain vanilla Carapace -> action/Retune return without duplicates

## 28. Resource/action matrix

For every gameplay resource:

- zero state
- one point
- full cap
- generation
- decay
- deliberate spend/conversion
- automatic spend
- insufficient-resource failure
- save/reload

Resources include:

- Brace / Impact / Heat / Mire / Rime
- Stress / Dawn / Dusk / Cadence / Release
- Reserve / Mend / Bastion / Wake
- Embers / Kiln / Rush / Haze
- Pressure / Stitch / Scout / Delegated Load / movement streak

Every deliberate failure must spend neither resource nor energy.

Every successful primary action must use one normal 1000-energy action.

## 29. Tighten/health regression matrix

Near vanilla's low-health warning threshold:

1. record Toughness, HP/max HP, AV/DV, Brace
2. use vanilla Tighten Carapace
3. hold position and build Brace
4. move and lose Brace
5. repeat while wounded

Pass criteria:

- Brace changes do not change Toughness/max HP
- MM does not repeatedly retrigger the low-health warning through stat churn
- vanilla Tighten still produces its own normal shell posture behavior
- Biology/resource descriptions remain coherent

## 30. Damage/contact runtime matrix

With DEV trace enabled:

- one melee hit with a primed contact resource
- one non-adjacent ranged hit with a primed contact resource
- one adjacent ranged hit while already engaged
- one incoming ordinary damage event
- one incoming environmental damage event
- one synthetic MM bonus-damage event

Verify:

- no recursive proc cascade
- one intended resource spend per qualifying exchange
- noncontact ranged damage does not incorrectly consume melee-contact resources
- environmental incident count is known before any dedupe is added
- branch messages correspond to actual dispatch/observed result semantics

## 31. Controller matrix

- inspect reactions
- inspect modifiers
- inspect ecology
- invoke primary action through Biology
- cancel nested pickers
- Retune
- Evolve
- scroll long pages/options

No normal gameplay path may require typed input.

## 32. Remaining architectural debt after runtime proof

These are not hidden blockers but are deliberately deferred from this recovery pass unless runtime evidence elevates them:

- Biology remains split across several partial files; consolidation is file-motion/maintenance debt, not a current gameplay fix.
- action names/descriptions and some cap/resource presentation still live in Biology-side providers rather than fully concrete mutation telemetry interfaces.
- environment predicates remain heuristic.
- obsolete `Register(GameObject)` and `Popup.ShowOptionList` APIs remain warnings on the supported target and should migrate only against verified replacement signatures.
- the adaptive base is still broad and display-name-driven in places; production refactoring belongs under the 1.0 stabilization freeze once behavior is proven.

## 33. Acceptance standard

The static implementation is not the release authority.

`0.7.1` is acceptable only when actual play demonstrates the Qud-shaped lifecycle:

> mutation gained -> Evolve + primary action exist -> rank-3 identity changes the action and unlocks Retune -> resources are visible -> deliberate action uses the normal ability surface -> automatic reactions are explainable -> mutation removal/dormancy removes its owned controls -> save/reload reconstructs the exact set -> one global Biology inspector summarizes the body without becoming a second mutation engine.

Until the exact branch passes the installed Qud compiler and runtime matrix, it remains a stabilization candidate rather than a verified release.
