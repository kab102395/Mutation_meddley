# Mutation Meddley v0.7.1 — Qud-Native Stabilization Implementation Audit

This document records what was actually changed during the Qud-native stabilization sweep and what intentionally remains behind runtime verification gates.

The governing plan is `docs/V0.7.1_QUD_NATIVE_STABILIZATION_SWEEP.md`.

## 1. External structure review

The sweep was checked against the normal Caves of Qud modding patterns documented for:

- mutations owning their own activated abilities and command events
- `PlayerMutator` for new-game player initialization
- `CallAfterGameLoaded` for existing saves
- ordinary parts as compositional game-object behavior
- 1000 energy as a normal action and zero-energy inspection as a free UI operation
- avoiding Harmony when the normal part/mutation/event surfaces are sufficient

The resulting architecture deliberately uses ordinary parts, mutation events, activated abilities, and the existing serialized mutation envelope. No Harmony patch was added.

## 2. Player-global Biology bootstrap

The original `0.7.1` build depended too heavily on the Biology support part being installed at the correct moment. It compiled, but hands-on testing showed that neither the Biology inspector nor the new action abilities reliably appeared on a new character.

The stabilized bootstrap now has four independent paths:

1. `PlayerMutator` installs Biology on new-game player creation.
2. `CallAfterGameLoaded` installs/refreshes Biology on loaded saves.
3. Every adaptive MM mutation defensively ensures Biology when the mutation is registered/gained.
4. Every adaptive MM mutation checks the support again during normal EndTurn lifecycle.

The global lifecycle hooks treat their input as the player by contract rather than depending on `IsPlayer()` already being observable during early character construction.

Mutation-side repair remains player-guarded so ordinary NPC mutation objects do not acquire player-global UI parts.

## 3. Mutation-owned primary actions

The first `0.7.1` implementation made `MutationMeddley_BiologySupport` own all five mutation action abilities.

That was replaced.

Each `MutationMeddley_AdaptiveMutationBase` instance now:

- registers its own primary-action command event
- adds/removes its own primary activated ability
- keeps the ability synchronized with functional activity and evolution identity
- replaces the button when the rank-3 identity changes
- updates the description without recreating the button when only live state changes
- removes the action on mutation removal
- removes the action while Carapace Evolution is dormant

This matches the ownership model already used successfully by the mod's Evolve/Retune mutation abilities and by normal Qud mutation examples.

## 4. Primary-action persistence without new public fields

No new public serialized fields were added to the established mutation classes.

Primary-action lifecycle state uses two metadata keys inside the existing `MutationMeddley_EvolutionState` envelope:

- `primary_action_guid`
- `primary_action_signature`

This preserves the existing public field layout while allowing old saves, stale GUIDs, branch changes, and missing ability entries to self-heal.

The first `0.7.1` Biology support public action-GUID/signature fields are intentionally retained for binary compatibility, but they are now migration-only. If they reference an old support-owned action ability, Biology removes that obsolete ability and clears those legacy values.

## 5. Retune lifecycle correction

`Retune ...` no longer exists before an actual stance exists.

Before the stabilization sweep, rank-1/rank-2 characters received Retune even though the only result was a message saying no stance was available.

Now:

- rank 1/2: no Retune button
- rank 3 identity chosen: Retune appears
- Carapace Evolution dormant: Retune disappears
- current stance selected again: no energy spent
- actual stance change: normal 1000-energy action

## 6. Biology remains player-global and read-mostly

`Mutation Meddley Biology` remains one player-global inspector rather than one copy per mutation.

It owns only the aggregate UI surface:

- owned MM mutation list
- current resource summaries
- automatic reaction summaries
- MM modifier summaries
- active ecology/synergy summaries

Mutation action command events are no longer registered on the Biology support part.

The Biology menu and the ordinary activated-ability button both route into the same primary-action transaction, so there is one gameplay implementation per action path rather than a UI-only duplicate effect.

## 7. New-game ordering defense

New-game player construction is explicitly treated as an ordering problem.

The Biology support part creates the universal inspector even if the first scan occurs before the mutation list is populated. Once mutation creation completes, the mutation lifecycle and Biology's normal refresh discover the final MM mutation set.

This prevents an empty early mutation scan from permanently deleting the inspector.

## 8. Existing-save defense

After loading a save:

- the after-load hook ensures Biology
- stale legacy support-owned actions are removed
- mutation-owned primary actions repair themselves from the current mutation/evolution state
- missing/stale action GUIDs are recreated
- branch signature mismatch causes one clean replacement
- the existing evolution/resource envelope is preserved

No old evolution IDs, hidden progress keys, stance state, or resource keys are intentionally reset.

## 9. Biology scan/performance cleanup

The initial defensive implementation called a full Biology refresh from every mutation-side `EnsureInstalled` invocation.

With several MM mutations this could rescan/update the player-global Biology surface multiple times per turn.

The stabilized implementation separates:

- **ensure** — make sure the part exists
- **refresh** — rebuild the player-global description/UI state

Mutation-side lifecycle performs ensure only.

The player-global Biology part refreshes itself once per EndTurn, on open, and from the authoritative new-game/load hooks.

## 10. No-MM character churn correction

Because PlayerMutator runs for every new player, Biology may be installed before it is known whether the finished character owns an MM mutation.

The first defensive version would create Biology, discover no MM mutations, remove it, and then recreate/remove it again on every later turn.

That loop is fixed.

After normal gameplay begins:

- no owned MM mutation -> Biology ability is removed and remains removed
- later MM mutation gain -> mutation lifecycle ensures the support; normal EndTurn restores the inspector
- owned MM mutation -> one normal Biology refresh per turn

## 11. Former-player/body-swap defense

The Biology support class was introduced as an ordinary serialized `IPart`, and changing its base serialization model mid-test-build is unnecessarily risky.

Instead, the support now becomes inert when its body is no longer the player:

- its Biology ability is removed
- first-`0.7.1` legacy action abilities are removed
- player UI is not maintained on a former player body

This keeps the current serialized class layout while preventing the player-global UI layer from behaving like ordinary NPC biology.

## 12. Resource telemetry corrections found by the sweep

The static audit found concrete cases where the UI-side duplicate cap formula could disagree with the mutation mechanics.

### Ash Metabolism

The first Biology implementation counted:

- base Ember cap
- Flaming Ray modifier

but omitted the live lit-cell Photosynthetic Skin modifier used by the mutation itself.

The displayed Ember maximum now includes both modifiers.

### Walking Colony

The first Biology implementation used a loose approximation for the second Pressure-cap body-plan bonus.

The current telemetry mirror now matches the actual known `BODY_PART_INTERACTION` vanilla registry used by this release:

- Carapace
- Multiple Legs
- Quills
- Burrowing Claws

Multiple Legs retains its separate capacity bonus, while one compatible additional body-plan mutation supplies the second bonus.

This remains marked for a later complete concrete-telemetry refactor so Biology stops carrying any copied cap formulas at all.

## 13. Passive-stat/max-HP repair retained

The previous `0.7.1` HP fix remains part of this stabilization:

- fast-changing Brace no longer changes Toughness/max HP
- unevolved Brace contributes shell defense instead
- passive stat refresh builds a desired snapshot first
- Qud stat shifts are changed only when the final value actually changes
- unchanged Toughness is not deliberately zeroed and immediately re-added each movement/damage refresh

This specifically protects the vanilla low-health threshold and `Tighten Carapace` interaction from Mutation Meddley-driven max-HP churn.

## 14. Spiteful Wall audit

Static inspection confirmed an architectural contradiction:

- concrete Carapace processing still contains the historical engaged Brace decrement
- shared stabilization logic restores that point so simply remaining engaged does not net-consume Brace

The net player behavior therefore remains the intended one, but the internal cancel/re-add is still technical debt.

It is intentionally not rewritten in this sweep because editing the large concrete Carapace state machine without runtime proof would create more risk than the compensating path. A later concrete-class cleanup should remove both sides together.

## 15. Direct-heal scaling audit

Static inspection confirmed direct `ParentObject.Heal(...)` paths that bypass the shared rank-4/7/10 verb-scaling helper:

- Carapace/Regeneration stationary recovery
- Brineborn Draw Brine automatic recovery
- Walking Colony Knit Flesh automatic recovery

These are now explicitly tracked as concrete-mutation cleanup items.

They were not blindly intercepted from the shared base because doing so would risk scaling unrelated healing events or double-scaling already-correct `MutationMeddley_TryHeal(...)` calls.

The correct fix is local to each concrete mutation and requires exact runtime regression around the affected branch. Until that pass, the shared deliberate actions and shared reaction heals continue to use the scaled helper; the three listed historical direct-heal paths remain exceptions.

## 16. Damage event audit

The sweep retained the existing explicit bonus-damage dispatch semantics rather than flattening them.

The runtime differentiates:

- damage event dispatched
- event continuation result
- observed HP loss

A static audit found that not every consumer necessarily needs the same interpretation. No global replacement was made without branch-by-branch proof.

## 17. Damage-event duplication research gate

The mutation roster listens to both `TookDamage` and `TookEnvironmentalDamage` in several places.

The supported build has not yet provided runtime evidence establishing whether a single environmental incident can arrive through both registered event names.

No speculative dedupe was introduced.

Mandatory test:

- enable DEV damage trace
- take one controlled environmental damage incident
- count incoming reaction passes/resource changes
- only add a transaction dedupe if one incident demonstrably enters twice

## 18. Adjacent-ranged contact research gate

The current conservative offensive-contact gate uses adjacency plus melee-engagement context.

The known edge case remains an adjacent ranged hit made while the attacker is already engaged in melee.

No guessed attack-type API was introduced.

Mandatory test:

- prime an Impact/Scout/Wake/Rush-style contact meter
- remain engaged with an adjacent target
- use a ranged attack at adjacent distance
- verify whether the meter spends
- inspect DEV trace before changing the contact classifier

## 19. Environment predicate audit

Current wet/saline/hot/smoky behavior still contains heuristics.

The sweep does not replace working heuristics with unverified APIs.

This is deliberately deferred to the `0.8` environment subsystem, where predicates can be centralized and proven against the supported build.

## 20. Serialization audit

The sweep avoids a mid-release conversion to `IScribedPart` even though Qud recommends the scribed model for new migration-friendly part code.

Reason:

- the current classes/public fields already exist in user test saves
- changing serialization strategy now creates a migration problem of its own

For `0.7.1`, preserving stable field layout is safer.

For a later production refactor, a deliberate migration to scribed parts can be evaluated with dedicated old-save fixtures.

## 21. Static API-risk policy

No new unverified Qud API was introduced for:

- HUD injection
- liquid semantics
- gas semantics
- attack-type classification
- minimal-event rewrites
- body-plan mutation

The stabilization work intentionally reuses APIs already present in the mod or documented in Qud's modding references:

- `PlayerMutator`
- `CallAfterGameLoaded`
- `RequirePart`
- mutation `Register`/`Mutate`/`Unmutate`
- activated abilities
- normal events
- `UseEnergy`

## 22. Mandatory runtime gate for this implementation

The exact stabilization commit is not considered compile-verified until tested by the user's installed Qud build.

### Compile gate

1. `git pull --ff-only`
2. `bash tools/check.sh`
3. `bash tools/deploy.sh`
4. fully restart Qud
5. `bash tools/logs.sh`
6. require `Success :)` for the exact Mutation Meddley source set

### New-game gate

Create a new character with vanilla Carapace + Carapace Evolution + Walking Colony.

Before intentional combat:

- `Mutation Meddley Biology` must exist
- `Brace Shell` must exist
- `Redistribute Pressure` must exist
- no Carapace/Colony Retune ability should exist before rank 3

After one ordinary turn, the same set must still exist with no duplicates.

### Rank-3 gate

At rank 3:

- choose Carapace identity
- old baseline action disappears
- exactly one branch action appears
- exactly one Retune Carapace ability appears
- same behavior for each other flagship mutation

### Save/reload gate

After save/reload:

- one Biology ability
- one primary action per active MM mutation
- one Retune per evolved/active MM mutation
- no early-0.7.1 support-owned duplicate actions
- resources/evolutions unchanged

### Tighten gate

Around the vanilla low-health warning threshold:

- repeatedly Tighten/untighten Carapace
- hold position and build Brace
- move and lose Brace
- Toughness/max HP must not oscillate because of Brace
- low-health warning must only reflect real threshold transitions

### Action transaction gate

For every primary action:

- invalid use -> no resource/no energy
- successful use -> expected resource conversion and 1000 energy
- Biology invocation -> exactly same result as bottom-bar invocation

### Controller gate

All Biology navigation and action invocation must work with controller only.

## 23. What remains intentionally unfinished after the static sweep

The following are known, bounded issues rather than hidden assumptions:

1. three historical direct-heal paths still bypass shared continuous verb scaling
2. Spiteful Wall still has an internal decrement/restore pair even though net behavior is correct
3. some Biology telemetry still mirrors concrete formulas instead of calling concrete read-only providers
4. environment semantics still include heuristics
5. adjacent-ranged contact classification needs runtime proof
6. environmental damage double-event behavior needs runtime proof
7. nonserialized applied-stat cache behavior needs save/reload runtime proof
8. the first `0.7.1` Biology implementation remains split across partial files; consolidation is deferred until behavior is proven so file-motion does not obscure regressions

None of those items justify guessing at Qud internals. They remain explicit gates for later cleanup.

## 24. Acceptance standard

The stabilization sweep is successful only if actual play demonstrates that the UI and mechanics now follow one understandable Qud-shaped lifecycle:

- mutation gained -> mutation action appears
- rank-3 identity -> action evolves + Retune appears
- resource changes -> description/biology updates
- automatic reaction -> Biology can explain why and at what deterministic chance
- mutation removed/dormant -> mutation-owned action disappears
- save/reload -> exact ability set reconstructs without duplication
- Biology -> one player-global inspector, not a second mutation engine

The runtime test, not the static plan, is the final authority.
