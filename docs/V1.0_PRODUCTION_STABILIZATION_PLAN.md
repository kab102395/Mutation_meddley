# Mutation Meddley v1.0.0 — Living Systems Production Stabilization Plan

## Release thesis

`1.0.0` is not the release where Mutation Meddley becomes dramatically larger.

It is the release where the project becomes stable, coherent, maintainable, understandable, performant, save-safe, controller-friendly, and credible as a finished Caves of Qud mod.

The release thesis is:

> **Nine mutation systems, one coherent ecology, stable enough for a full campaign.**

The player-facing identity is:

> **Your build is not a list of mutations anymore. It is a body.**

The engineering identity is equally important:

> **Mutation Meddley 1.0 should be a system we can maintain after release without constantly reopening foundational architecture decisions.**

`0.6.x` established functional verbs and branching.

`0.7.x` established continuous progression.

`0.8.x` establishes ecology, environmental integration, liabilities, and deeper cross-system interactions.

`0.9.x` expands the ecosystem with four additional flagship mutation families.

`1.0.0` is the production-quality stabilization pass across everything that already exists.

---

# 1. Hard feature freeze

## 1.1 Roster freeze

Assuming the `0.9.x` plan lands as intended, the 1.0 roster is frozen around nine major gameplay systems:

1. `Carapace Evolution`
2. `Living Crystal`
3. `Brineborn`
4. `Ash Metabolism`
5. `Walking Colony`
6. Storm Organ / final electrical-ecology name
7. Mycelial Communion / final fungal-ecology name
8. final Neural / Signal ecology mutation
9. `Chrome Marrow`

`1.0.0` should not add another flagship mutation merely because an idea is compelling.

A release candidate should be allowed to remove or simplify content if a system is not earning its complexity.

## 1.2 No major new frameworks

The following are out of scope for `1.0.0` unless a blocking production defect proves one is required:

- no mutation crafting framework
- no procedural mutation generation
- no new evolution tier beyond the established rank milestones
- no global respec architecture
- no custom faction framework
- no custom quest framework
- no custom world-region framework
- no cybernetics rewrite
- no new persistence envelope
- no major replacement of Qud's body system
- no new global synergy manager
- no speculative Harmony layer
- no replacement character-creation system

## 1.3 What 1.0 may still change

The feature freeze does not mean the current behavior is sacred.

`1.0.0` may:

- remove weak synergies
- replace passive-heavy mechanics with cleaner existing verbs
- reduce or increase numbers
- simplify state
- rename internal helper methods where save compatibility is unaffected
- refactor generic architecture
- migrate obsolete Qud APIs after verification
- improve controller UX
- improve descriptions and feedback
- fix event semantics
- fix performance problems
- fix save compatibility
- remove dead code

The rule is:

> **Stabilize and clarify what exists. Do not widen the game-design surface.**

# 2. 1.0 release pillars

The production pass has fourteen primary pillars:

1. Complete branch-quality audit.
2. Balance normalization.
3. Action-economy normalization.
4. Technical-debt cleanup.
5. Generic-framework cleanup.
6. Environment-predicate correctness.
7. Contact and damage-event correctness.
8. Resource transaction consistency.
9. Save compatibility as a release contract.
10. Synergy / triad / hidden-adaptation quality pruning.
11. Player-facing UX and controller polish.
12. Performance and event-volume validation.
13. Documentation / Workshop productionization.
14. Multi-hour campaign validation.

No single pillar is sufficient by itself.

A mod that compiles but is unreadable is not 1.0-ready.

A mod that is fun but corrupts old saves is not 1.0-ready.

A mod that is stable but only feels good on keyboard/mouse is not 1.0-ready for the intended Steam Deck target.

# 3. Full branch audit

Every rank-3 identity across the entire roster receives a formal production review.

## 3.1 Branch scorecard

Each branch should be scored against the following contract:

| Category | 1.0 requirement |
| --- | --- |
| Identity | recognizable within a few turns |
| Signature verb | player deliberately does something different |
| Resource loop | generation and spending are legible |
| Rank-3 choice | changes behavior rather than only stats |
| Stances | both alter tactical decisions |
| Rank-6 split | creates two distinct operating styles |
| Rank-9 endpoint | completes the branch instead of replacing it |
| Hidden endpoint | alternative rather than secret strict upgrade |
| Liability | materially affects play |
| Solo viability | branch remains useful without its best synergy |
| Ecology | environment/other mutations extend the loop |
| Rank scaling | ranks between milestones remain worthwhile |
| Feedback | player can tell when the loop worked |
| Controller use | no typing or awkward desktop-only interaction |

## 3.2 Failure criteria

A branch should not ship unchanged if multiple statements are true:

- the player cannot explain what they should be doing
- the branch is mostly passive stats
- one stance is always superior
- rank 6 changes only numbers
- rank 9 replaces the lower-rank loop
- hidden rank 9 is simply stronger than normal rank 9
- the branch requires a specific synergy to be viable
- liability is irrelevant
- liability is arbitrary punishment
- resource state is mostly invisible
- resource generation is accidental rather than deliberate
- continuous rank scaling is technically present but imperceptible

## 3.3 Audit order

Audit mutation families in this order:

1. original 0.6-era systems
2. 0.8 ecology-upgraded systems
3. 0.9 new systems
4. cross-system builds

This order helps identify whether newer content power-crept older content.

# 4. Balance normalization

By 1.0 the project will contain mechanics created across multiple design generations.

Numbers must be normalized deliberately.

## 4.1 Acquisition-cost audit

For every mutation, record:

- character-creation mutation-point cost
- baseline rank-1 power
- rank-2 value
- rank-3 qualitative gain
- rank-6 gain
- rank-9 gain
- continuous rank contribution
- solo reliability
- synergy ceiling
- environmental dependence
- liability severity

Starting cost should correspond to practical value, not age of implementation.

## 4.2 Defensive-stat audit

Search the entire codebase for every contribution to:

- AV
- DV
- Toughness
- Agility
- Willpower
- Ego
- Intelligence
- Quickness
- Heat resistance
- Cold resistance
- electrical resistance if used
- other direct defensive modifiers

Create a table containing:

- owning mutation
- branch
- rank requirement
- stance requirement
- environment requirement
- synergy requirement
- triad requirement
- maximum simultaneous stack

Special scrutiny should be applied to AV and Quickness because small increments can be disproportionately strong in Qud.

## 4.3 Damage audit

For every synthetic or direct Mutation Meddley damage effect, record:

- source mutation
- required resource
- damage magnitude
- continuous scaling
- rank gate
- target type
- contact requirement
- recursion protection
- frequency
- whether it can occur multiple times per turn
- whether multiple mutation systems can fire on the same attack

The goal is not identical damage across mutations.

The goal is deliberate output budgets.

## 4.4 Healing audit

Inventory all healing paths, including direct calls that may bypass shared scaling helpers.

For every heal:

- amount
- frequency
- rank scaling
- branch gate
- environment gate
- resource cost
- wound requirement
- synergy contribution
- direct versus shared helper path

Ensure older direct-heal paths have not accidentally fallen outside intended continuous progression.

## 4.5 Resistance audit

Avoid broad resistance inflation.

Environmental branches should be strong because they change how environments are used, not merely because all relevant resistance values approach immunity.

## 4.6 Resource-economy table

For every resource/state, document:

- cap
- baseline generation rate
- best-case generation rate
- typical spend size
- expected turns to prime
- expected turns to decay
- stance changes
- rank scaling
- pair-synergy changes
- triad changes
- capstone changes

Candidate resource list by the time 1.0 arrives may include:

- Brace
- Impact
- Heat/Mire/Rime or equivalent Carapace state
- Stress
- Dawn
- Dusk
- Cadence
- Release
- Reserve
- Mend
- Bastion
- Wake
- Embers
- Kiln
- Rush
- Haze
- Colony Pressure
- Stitch
- Scout
- Parliament
- Charge
- Overload
- Bloom
- Signal / Pattern
- Integration
- Strain

Some resources should be fast and tactical.

Some should be slow and strategic.

None should be fast or slow by accident.

# 5. Action-economy normalization

`1.0.0` must define predictable energy semantics.

## 5.1 Classify every interaction

Every gameplay effect should be categorized as one of:

- passive generation
- passive decay
- free reaction
- attack-driven reaction
- movement-driven reaction
- environmental reaction
- EndTurn processing
- explicit activated ability
- stance change
- evolution choice
- UI-only action

## 5.2 Stance policy

Production target:

- selecting the currently active stance should not consume a full action
- actually switching stance may consume energy if that is a deliberate balance rule
- all mutations should follow a consistent stance-cost philosophy
- cancellation should never consume a turn
- a failed option-picker interaction should not consume energy
- stance switching should never duplicate passives
- stance switching should never erase continuous progression bonuses

The known same-mode 1000-energy behavior must be resolved or explicitly justified before 1.0.

## 5.3 Evolution-choice policy

Evolution UI should:

- not accidentally fire multiple times
- survive cancellation
- not spend a tier on invalid selection
- remain controller-usable
- preserve previously selected tiers
- never silently auto-select an alternative because a UI call failed

## 5.4 Activated abilities

For each activated ability:

- verify energy cost
- verify cooldown if any
- verify cancellation
- verify target failure behavior
- verify resource spend ordering
- verify message behavior

# 6. Obsolete Qud API migration

Current development builds have historically compiled with obsolete API warnings around registration and option-list selection.

`1.0.0` is the right time to investigate replacing those APIs.

## 6.1 Registration migration

Known warning family:

- `Register(GameObject)`
- recommended newer registration path involving `IEventRegistrar`

Migration procedure:

1. inspect the exact installed Qud assemblies
2. inspect current supported scripting examples
3. verify the expected base-class lifecycle
4. migrate one low-risk class first
5. compile in Qud
6. verify event registration at runtime
7. save/reload
8. migrate remaining classes only after success

Do not change registration simply to silence a warning if runtime behavior is less certain.

## 6.2 Picker migration

Known warning family:

- `Popup.ShowOptionList`
- recommendation toward `PickOption`

Migration requirements:

- controller navigation must remain at least as good
- cancellation must remain safe
- text wrapping must remain usable on Steam Deck
- result semantics must be verified
- no typed-number UI is acceptable

If the newer API is verified and controller-safe, 1.0 should ideally ship using it.

If not, document the retained deprecated call and why it remains.

## 6.3 Warning budget

Release goal:

- zero avoidable compiler warnings from Mutation Meddley code
- any intentionally retained warnings documented
- no unresolved warning should hide a real warning during user diagnosis

# 7. Framework architecture cleanup

The rapid static-freeze and progression passes intentionally centralized some mutation-specific logic for safety.

That was acceptable during development.

It should not become the permanent 1.0 architecture.

## 7.1 Desired responsibility boundaries

### `MutationMeddley_EvolvingMutationBase`

Should own generic concerns such as:

- tier tracking
- evolution selection
- serialized envelope support
- discovery state helpers
- generic mutation lifecycle
- common save-safe utilities

### `MutationMeddley_AdaptiveMutationBase`

Should own generic adaptive concerns such as:

- environment queries
- semantic tags
- synergy eligibility helpers
- continuous progression helpers
- shared damage dispatch plumbing
- shared contact classification
- generic UI/readout formatting
- generic ecology-history support where appropriate

### Concrete mutation classes

Should own:

- branch resource generation
- branch resource spending
- mutation-specific passives
- liabilities
- stances
- pair-synergy behavior
- triad behavior
- hidden adaptation conditions
- mutation-specific clue text
- capstone behavior

## 7.2 Remove display-name dispatch

Production target:

Generic base classes should not contain large behavior blocks like:

- `if this mutation is Walking Colony...`
- `if DisplayName == Brineborn...`

Where these exist, move behavior into narrow mutation-specific overrides.

## 7.3 Prefer virtual hooks over central switch blocks

Potential hook categories:

- apply continuous progression passives
- get baseline resource cap
- append current-state readout
- handle entered-cell mutation behavior
- handle end-turn mutation behavior
- handle incoming damage mutation behavior
- handle outgoing contact mutation behavior
- evaluate mutation-specific liabilities

Exact method names should be chosen from the final code shape rather than copied from this plan.

## 7.4 Refactor safety rules

Architecture cleanup must not:

- rename persistent evolution IDs
- rename serialized public fields without migration
- reset state envelopes
- change branch outcomes merely due to method movement
- alter resource values unless part of an explicit balance change

Refactor one mutation family at a time and run behavioral regression tests between each family.

# 9. Contact classification completion

The contact classifier was intentionally conservative during earlier releases.

`1.0.0` should resolve remaining ambiguity as far as Qud's event surface allows.

## 9.1 Adjacent ranged edge case

Investigate whether Qud exposes a trustworthy distinction between:

- actual melee contact
- adjacent ranged attack
- synthetic Mutation Meddley damage
- environmental damage
- indirect damage

Use:

- installed assemblies
- actual event payloads
- DEV traces
- repeatable test cases

If reliable distinction exists, implement it.

If it does not, document the edge case and ensure no exploit or catastrophic meter loss results.

## 9.2 Contact test matrix

For every contact-spending resource:

- adjacent melee hit
- adjacent melee miss if relevant
- non-adjacent ranged hit
- adjacent ranged hit
- thrown item if relevant
- environmental damage
- synthetic Mutation Meddley damage
- retaliation damage
- target removed before spend
- attacker removed before resolution

No close-contact resource should be consumed outside its intended semantic context.

# 10. Damage-event semantics

## 10.1 Environmental double-fire audit

Resolve whether Qud can dispatch both generic damage and environmental-damage events for one underlying incident.

Specifically test interactions analogous to:

- `TookDamage`
- `TookEnvironmentalDamage`

The goal is to establish explicit semantics for Mutation Meddley.

## 10.2 One incident, one intended resource effect

A single damage incident should not accidentally:

- generate the same meter twice
- spend the same meter twice
- trigger duplicate hidden progress
- emit duplicate tactical messages

unless the mechanic is explicitly documented as reacting to two distinct components.

## 10.3 Synthetic damage contract

Mutation Meddley bonus damage must retain:

- cross-mutation recursion protection
- correct source/target resolution
- failure-safe resource semantics
- separation between event continuation and observed HP loss

The established distinction between dispatch success, event continuation, and observed damage should remain explicit.

# 11. Resource transaction model

By 1.0 all resources should follow consistent transaction semantics.

## 11.1 Generation sequence

Preferred sequence:

1. verify owner is functionally active
2. verify trigger context
3. calculate generation
4. apply branch/synergy modifiers
5. clamp
6. update state
7. emit tactical feedback only if useful
8. advance ecology history if required

## 11.2 Spend sequence

Preferred sequence:

1. verify trigger
2. verify required resource
3. resolve target/context
4. reserve or consume according to declared mechanic
5. attempt payoff
6. determine success/failure
7. refund only if mechanic explicitly allows it
8. record history/discovery
9. emit feedback

## 11.3 Failure policy

Each verb must define what happens when:

- target vanishes
- target is invalid
- event is cancelled
- damage is fully prevented
- heal target is already full
- environment changes before resolution
- partner mutation becomes dormant

Do not let failure behavior emerge accidentally from code ordering.

## 11.4 Cross-mutation conversions

If mutation A converts its state into mutation B state:

- A owns the subtraction
- B owns the addition
- order is deterministic
- neither mutation writes directly into unrelated private implementation fields
- recursion is guarded
- partial failure behavior is defined

# 12. Save compatibility becomes a product contract

By 1.0 save safety is no longer a convenience.

It is a release requirement.

## 12.1 Supported save generations

Create representative saved characters from:

- 0.6.x
- 0.7.x
- 0.8.x
- 0.9.x
- 1.0 release candidate

## 12.2 Required scenarios

Maintain save fixtures for characters with:

- rank-1 mutation only
- rank-3 identity
- rank-6 specialization
- normal rank-9 capstone
- hidden adaptation discovered but not selected
- hidden adaptation selected
- multiple hidden discoveries
- dormant Carapace Evolution
- multiple Mutation Meddley mutations
- high ecology-history values
- active stance selections
- high stored resources
- Chrome Marrow Integration/Strain
- Neural target-independent persistent state
- Mycelial persistent history
- Storm hidden-progress state

## 12.3 Load guarantees

Loading an older supported save must never silently:

- select a new branch
- switch a rank-6 choice
- change a rank-9 choice
- reveal an undiscovered secret
- erase a discovered secret
- reset valid persistent history
- activate dormant Carapace ecology

## 12.4 Missing state

New state introduced after a save was created must:

- default safely
- avoid null-sensitive behavior
- not require a manual migration command

## 12.5 Unknown state

Unknown state-envelope keys should be preserved where the envelope contract already supports that behavior.

## 12.6 Transient references

Do not serialize:

- target GameObject references
- current event references
- recursion guard references
- temporary cell references
- UI callbacks

Persistent state should remain IDs, numbers, booleans, and other intentionally serializable values.

# 13. Dead-state and residue audit

Over multiple development cycles the project will accumulate historical state.

1.0 should explicitly inventory it.

## 13.1 For every state key

Find:

- all writers
- all readers
- default value
- save compatibility significance
- whether current gameplay still needs it

## 13.2 Categories

Classify keys as:

- active gameplay
- compatibility-only
- DEV-only
- obsolete but tolerated
- safe to remove

## 13.3 Living Crystal cadence residue

Previously identified dead or mutually exclusive cadence-related residue must be revisited during this audit.

Either:

- restore a meaningful gameplay role
- remove active behavior while tolerating legacy save keys

Do not retain meaningless mechanics solely because they once existed.

## 13.4 Hidden-cap meter asymmetry

The historical asymmetry in some hidden capstone meter caps should receive an explicit balance decision.

By 1.0 it must be either:

- documented intentional behavior
- normalized

No unresolved “maybe intentional” items should remain in the release checklist.

# 14. Synergy pruning

The 1.0 ecology should be curated, not exhaustive.

## 14.1 Retention test

A named pair synergy should remain only if at least one is true:

- changes a player decision
- changes resource routing
- creates a recognizable archetype
- creates meaningful risk/reward
- materially changes a verb
- enables a hidden adaptation path
- solves a branch-specific problem in an interesting way

## 14.2 Weak-synergy candidates

Named relationships that are only:

- +1 DV
- +small resistance
- +minor attribute
- passive uptime with no tactical implication

should be considered for:

- conversion into a more meaningful mechanic
- demotion into an unnamed minor passive
- removal

## 14.3 Solo viability rule

No mutation branch should require a named synergy to feel complete.

Synergies should extend or redirect.

They should not rescue incomplete baseline design.

---

# 15. Triad quality audit

Every triad should answer:

> **If the triad-specific implementation disappeared and only the three pair relationships remained, would the player notice?**

If the answer is no, the triad has not earned its name.

## 15.1 Required triad properties

Each retained triad needs:

- exact branch eligibility
- one coherent combined fantasy
- one coordinated mechanical sequence
- deterministic state ordering
- at least one meaningful tactical decision
- clear player feedback
- no uncontrolled three-way stat stacking

## 15.2 Coordinated verbs

Strong triad patterns include:

- A generates state for B
- B transforms it
- C determines the spend

or:

- three resources become temporarily convertible

or:

- one trigger causes ordered three-system resolution

## 15.3 Triad pruning

Remove or redesign triads whose main identity remains:

- permanent AV
- permanent DV
- generic Quickness
- unrelated simultaneous passive buffs

## 15.4 Stress testing

Every retained triad must be tested with:

- all three correct branches
- one missing mutation
- one wrong branch
- one dormant participant
- environment absent
- environment present
- save/reload
- stance change
- target failure
- recursion-prone combat

---

# 16. Hidden adaptation production audit

Hidden adaptations should become one of the defining 1.0 features.

## 16.1 Discovery quality

Every hidden adaptation should satisfy:

- understandable retrospective logic
- repeated behavior rather than possession alone
- fair discovery window
- no accidental impossible prerequisites
- multiple clue stages
- no exact counter in normal mode
- exact progress available in DEV mode

## 16.2 Player reaction target

Desired reaction:

> “Of course my body evolved this way after everything I have been doing.”

Undesired reaction:

> “I have no idea why this unlocked.”

## 16.3 Hidden choice balance

A hidden rank-9 adaptation must not simply dominate the normal capstone.

It should alter:

- resource routing
- environment preference
- liability
- stance interaction
- synergy topology
- tactical payoff

## 16.4 Late discovery

Preserve the established rule unless 1.0 explicitly changes it:

- once the relevant rank-9 tier has been spent, hidden discovery for that choice stops

If this remains the rule, player-facing clues must be sufficiently fair before rank 9.

# 18. Mutation-screen information architecture

By 1.0 all mutation descriptions should use a consistent hierarchy.

Recommended structure:

## Identity

Example:

`Hunter Shell -> Ravager Joints -> Skitter Bulwark`

## Operating loop

One concise tactical explanation.

Example:

`Move to build pursuit pressure. Close melee contact spends Impact.`

## Current resources

Show only relevant mutation-local states.

Example:

- `Impact: 4/6`
- `Integration: 5/7`
- `Strain: Loaded`

## Current stance

Name plus one-line purpose.

## Continuous growth

Show:

- mutation rank
- maturity tier
- verb-output bonus
- what the next normal rank contributes

## Active ecology

Show relationships that matter now.

Do not list every possible inactive synergy.

## Current liability

Explain the current risk or constraint plainly.

Examples:

- `Redline: Strain is increasing.`
- `Root Network: moving will break rooted growth.`
- `Predatory Cortex: changing targets will lose Pattern.`
- `Brineborn: dry ground is weakening Reserve generation.`

## Unusual adaptations

Only discovered names.

Exact undiscovered options remain hidden.

# 19. Message-spam policy

A mature event-driven mod can easily overwhelm Qud's message log.

1.0 requires explicit message severity.

## 19.1 Critical messages

Always display.

Examples:

- unusual adaptation discovered
- forced biomechanical shutdown
- branch-changing major event

## 19.2 Tactical messages

Display when the player needs to understand meaningful state conversion.

Examples:

- Impact discharged
- Salt Circuit overloaded
- critical Strain forced a vent

## 19.3 Ambient messages

Suppress or rate-limit.

Examples:

- +1 resource every ordinary turn
- repeated environment refresh
- passive state confirmation every cell

## 19.4 DEV messages

Only when DEV tracing is explicitly enabled.

No production player should see event plumbing, target IDs, or internal dispatch details during normal play.

# 21. Performance validation

Nine interacting systems make performance a release concern.

## 21.1 Hot event inventory

Audit code registered for frequently occurring events, especially:

- movement
- entered-cell
- EndTurn
- incoming damage
- outgoing damage
- melee contact
- environment refresh
- ability use

## 21.2 Forbidden hot-loop patterns

Avoid:

- reflection in combat handlers
- full-zone scans every turn
- repeated full mutation-list scans when a local query exists
- uncontrolled string parsing every movement step
- per-turn allocation of large temporary collections
- permanent temporary-world-object creation
- duplicate passive refreshes

## 21.3 Movement benchmark

Create a stress character with all available Mutation Meddley systems.

Traverse at least 1,000 cells across representative environments.

Observe:

- hitching
- log spam
- exceptions
- resource drift
- environment-state leaks

## 21.4 Combat benchmark

Use a fight with:

- melee attackers
- ranged attackers
- multiple targets
- environmental damage where possible
- multiple primed resources
- pair synergies
- triads

Validate no significant stutter attributable to Mutation Meddley.

## 21.5 Environment benchmark

Repeatedly cross:

- wet/dry
- saline/fresh
- lit/dark
- hot/normal
- smoke/clean

Check for steadily increasing per-turn cost or duplicated modifiers.

## 21.6 Long-session benchmark

Play several hours with repeated:

- zone transitions
- save/reload
- combat
- mutation leveling
- stance changes

Performance should not degrade over time due to leaked state or objects.

# 22. Mod-compatibility posture

1.0 does not promise compatibility with every other Qud mod.

It should, however, behave responsibly.

## 22.1 Namespace discipline

Continue prefixing project-owned identifiers with `MutationMeddley_` where Qud APIs allow it.

Avoid generic type names likely to collide with other mods.

## 22.2 Vanilla assumptions

Do not assume a vanilla mutation class has not been modified by another mod unless unavoidable.

Prefer capability checks and safe dormancy.

## 22.3 Global patches

Avoid global Harmony patches unless ordinary Qud events/parts cannot support an essential mechanic and the patch has been specifically justified and tested.

## 22.4 Known conflicts

Document known conflicts separately from Mutation Meddley bugs.

The historical `XRL.World.Parts.Experience` conflict produced by Endless EXP Scaling is an example of an external type conflict that can muddy tests without being caused by Mutation Meddley.

## 22.5 Graceful absence

If an optional partner mutation is absent:

- no exception
- no stale passive
- no hidden progress
- no triad eligibility

- active triads
- resource meters
- ecology-history values
- hidden progress
- machine classification
- recursion-guard state where useful

## 23.2 Normal-play isolation

DEV diagnostics must:

- stay disabled by default
- avoid message spam
- not change gameplay state unless explicitly used as a test action
- never be required for ordinary play

## 23.3 Release packaging

Decide whether DEV mutation visibility should be:

- hidden from normal character creation
- gated behind a dev configuration
- retained but clearly marked

Do not accidentally ship intrusive testing content as part of ordinary character creation.

---

# 24. Error containment

Production code should fail safely where possible.

## 24.1 Target failure

If a target disappears:

- do not crash
- preserve or refund resources according to declared verb policy

## 24.2 Environment failure

If an environment query cannot resolve:

- default to safe false/neutral behavior
- do not grant high-value effects optimistically

## 24.3 Dependency loss

If vanilla Carapace disappears:

- Carapace Evolution becomes dormant
- persistent choices remain
- ecology stops
- reactivation restores behavior safely

Equivalent companion patterns should follow the same philosophy.

## 24.4 Malformed state

If a state-envelope value is malformed:

- avoid throwing during normal load if a safe fallback exists
- preserve unrelated valid state
- avoid silently selecting new branches

## 24.5 Optional synergy failure

A broken optional synergy lookup should not disable the base mutation.

# 39. 1.0 exit criteria

Mutation Meddley `1.0.0` is complete only when all of the following are true:

## Architecture

- generic bases are substantially generic
- mutation-specific behavior lives primarily in mutation classes
- no uncontrolled central display-name behavior switch remains without explicit justification
- persistence architecture is documented

## Compilation

- exact release commit compiles in supported Qud
- source count is expected
- DLL is produced
- XML loads
- no Mutation Meddley startup exception

## Warnings

- avoidable warnings are resolved
- intentionally retained warnings are documented

## Progression

- every normal rank investment remains meaningful
- ranks 3/6/9 produce qualitative evolution
- rank 10 scaling remains coherent

## Branches

- every rank-3 identity has a clear verb
- every rank-6 choice changes play
- every rank-9 endpoint completes a build
- hidden rank-9 options remain alternatives

## Liabilities

- every major identity has a meaningful constraint
- constraints are understandable and manageable

## Resources

- generation/spending semantics are explicit
- resource caps are intentional
- no accidental negative or duplicate state

## Combat

- contact classification is as correct as verified Qud APIs permit
- ranged/non-contact damage cannot casually drain melee meters
- synthetic damage cannot recurse indefinitely
- damage-event duplication is controlled

## Environment

- predicates are documented
- representative cells pass tests
- known heuristics are documented

## Ecology

- named pairs have earned their names
- weak synergies are removed or demoted
- triads have coordinated behavior
- dormant participants do not contribute

## Secrets

- hidden progress persists
- clues are legible without spoilers
- discoveries are behaviorally justified

## Save compatibility

- supported old saves load
- branch choices remain intact
- hidden discoveries remain intact
- missing new state defaults safely

## Controller

- ordinary gameplay requires no typing
- all evolution/stance UI works with controller
- descriptions are readable on Steam Deck

## Performance

- stacked movement stress test is smooth
- combat stress test is smooth
- no resource or object leak is observed
- multi-hour sessions remain stable

## Documentation

- active docs match current code
- release checklist exists
- save and environment contracts are documented
- Workshop notes are ready

## Campaign validation

- structural build tested
- environmental build tested
- distributed biological build tested
- unoptimized mixed build tested
- repeated save/reload tested
- multi-hour ordinary play completed without structural Mutation Meddley failure

# 40. Post-1.0 philosophy

After 1.0, the project should stop behaving like a perpetual prototype.

New work should respect the stable contracts created here.

A new mutation introduced in `1.1` should plug into:

- continuous progression
- branch architecture
- liability design
- ecology topology
- resource transaction semantics
- hidden discovery rules
- save-state conventions
- controller UX

without requiring a rewrite of the foundation.

That is the real test of whether 1.0 succeeded.

---

# 41. Final design principle

A production-quality Mutation Meddley build should feel less like a collection of independently purchased powers and more like a body that has learned how to survive through its own history.

The player should understand:

- what the organism wants to do
- what it is storing
- what its environment is doing to it
- which parts of the body are cooperating
- what risk is accumulating
- why an unusual adaptation emerged

The complexity should live in the ecology.

The confusion should not.

The final standard for `1.0.0` is therefore:

> **Deep enough to support strange emergent builds, clear enough that the player understands their own body, and stable enough to trust for a full Caves of Qud campaign.**
